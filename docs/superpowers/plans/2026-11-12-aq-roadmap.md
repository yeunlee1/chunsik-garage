# AQ 점검 구현 로드맵

> 설계 문서 `docs/superpowers/specs/2026-11-12-aq-checkup-design.md`(이하 설계)의 24절 「만드는 순서」를 단계별 구현 계획으로 나눈 것이다. 단계마다 상세 계획을 따로 쓴다. 앞 단계가 끝나고 검증된 뒤에 다음 단계의 상세 계획을 쓴다. 앞 단계에서 배운 것(실제 기록의 모양, 성능 실측)이 다음 계획에 들어가야 하기 때문이다.

## 단계

| 단계 | 목표 | 끝나면 돌려 볼 수 있는 것 | 설계의 절 | 상세 계획 |
|---|---|---|---|---|
| 1 | Claude Code 기록 읽기, 날짜별 세션 요약, 캐시, 저장소 뼈대 | `aq doctor`(Claude Code 몫), 이 PC의 기록을 읽어 세션 요약의 합계를 내는 개발용 스크립트, 캐시를 켜고 끈 결과가 같다는 시험 | 6.3, 7.1~7.4, 8, 9.1~9.5, 9.7~9.8, 12.1, 20.1(읽기), 21.1(어댑터), 22 | `2026-11-12-aq-stage1-claude-code-reader.md` |
| 2 | 셋팅 스캐너(Claude Code 몫), 지표, 규칙 22개, 점수, 등급, 평가 결과, 문구, 상태 폴더 다루기(`aq where`, `aq clean`) | `aq checkup --no-open`이 평가 결과 JSON과 터미널 요약을 낸다. `aq where`와 `aq clean`이 그때까지 상태 폴더에 생긴 것(캐시 등)을 다룬다 | 10, 11, 12, 17(단서만), 19, 20 | 넷으로 나눈다. 1부 `2026-11-13-aq-stage2-1-setup-scanner.md`(셋팅 스캐너, 상태 파일과 관측 기록, `aq where`·`aq clean`), 2부 `2026-11-13-aq-stage2-2-evaluation-engine.md`(지표, 규칙 22개, 점수와 등급, 설치 판정, 정비 후보의 목록), 3부 `2026-11-13-aq-stage2-3-checkup-result.md`(평가 결과의 조립, 관측 기록과 이력의 저장, `aq checkup --no-open`), 4부 `2026-11-14-aq-stage2-4-copy-and-lang.md`(문구와 `--lang`) |
| 3 | 결과 화면(HTML 한 파일)과 공유 카드, 캐릭터 2차 그림 6장 | `aq checkup`이 결과 화면을 브라우저로 연다 | 13, 14, 13.3(그림) | 2단계 뒤에 쓴다 |
| 4 | 스킬(`skills/aq/SKILL.md`)과 Claude Code 플러그인, 버전 일치 검사 | 플러그인을 깔고 "AQ 점검해 줘"로 처음부터 끝까지 돈다 | 5, 7.1, 15, 23 | 3단계 뒤에 쓴다 |
| 5 | Codex 어댑터·스캐너·플러그인 | 두 도구를 함께 점검한다 | 9.6, 10(Codex), 18.3 | 4단계 뒤에 쓴다 |
| 6 | 정비(A1~A4)와 되돌리기 | `aq tune plan/apply/verify/undo`. `aq clean --all`이 정비 작업 기록까지 지운다는 것을 알린다 | 16 | 5단계 뒤에 쓴다 |
| 7 | 정밀 점검, 점수 이력, 세션 시작 알림 | `aq deep-hints`, 이력 그래프, `aq notify on/off/status`와 세션 시작 한 줄 | 17, 18 | 6단계 뒤에 쓴다 |
| 8 | README 두 벌, 공개 전 점검 | 정식 배포 준비 | 21.2, 23, 26 | 7단계 뒤에 쓴다 |

2단계는 한 계획으로 쓰기에 커서 네 상세 계획으로 나눈다. 앞의 부분이 병합되고 검증된 뒤에 다음 부분의 계획을 쓴다.

| 부분 | 내용 | 끝나면 돌려 볼 수 있는 것 |
|---|---|---|
| 1부 | 셋팅 스캐너(Claude Code), 상태 파일과 설치마다의 관측 기록, `aq where`·`aq clean` | `aq where`, `aq clean [--all]`, 이 PC의 셋팅을 읽어 종류별 개수를 내는 개발용 스크립트 |
| 2부 | 평가 엔진. 구간 합계와 지표, 규칙 22개, 점수와 등급, E5와 E6의 설치 판정, 정비 후보(A1~A3)의 목록, 분류와 심각도와 예상 효과, 입력 조립 | 이 PC의 기록과 셋팅으로 규칙 22개의 값, 점수, 등급을 숫자로 내는 개발용 스크립트 |
| 3부 | 평가 결과의 조립(도구 목록, 읽은 양, 사용 기록, 도구별 값의 관측 범위, 알림, 정밀 점검 단서), 터미널 요약과 실행 기록, 관측 기록과 이력과 결과 파일의 저장, 캐시 정리, `aq checkup [--no-open] [--no-save] [--rescan]` | `aq checkup --no-open`이 평가 결과 파일과 요약(문장은 아직 없다)을 낸다 |
| 4부 | 문구(영어와 한국어의 제목, 설명, 처방, 어떻게 쟀나, 못 잰 이유의 낱말, 알림, 진단과 별명, 덧붙이는 말)와 잰 값의 단위, `--lang`과 언어의 차례 | 2단계의 "끝나면 돌려 볼 수 있는 것" 전부 |

1부가 내는 셋팅 사실과 1단계의 세션 요약이 2부 규칙의 입력이고, 2부가 내는 평가가 3부가 조립하는 평가 결과의 재료다. 3부가 정한 결과의 모양과 근거 숫자에 4부가 문장을 붙인다. 2부를 다시 나눈 까닭은 1부를 나눌 때와 같다. 한 계획으로 쓰면 1부의 두 배쯤이 되어 리뷰가 길어지고, 평가 엔진을 실제 기록에 돌려 보기 전에 문구와 명령을 계획하게 된다. 3부를 다시 나눈 까닭도 같다. 문구는 결과의 모양이 정해지고 실제 기록에 돌려 본 뒤에 써야 칸이 정해진다(설계 「2단계 3부 계획에서 보완」).

## 모든 단계에 걸리는 약속

- 깃. 기본 브랜치는 `develop`이다. 단계마다 한글 이름의 작업 브랜치(예. `1단계-클로드코드-기록읽기`)를 `develop`에서 따고, 단계가 끝나면 병합 요청(PR)으로 `develop`에 합친다. `main`에는 배포할 때만 `develop`을 합친다.
- 검사. 깃허브 액션을 쓰지 않는다. 올리기 전에 로컬에서 `npm run check`를 돌려 통과를 확인하고, 병합 요청 본문에 로컬에서 돌린 검사와 결과를 적는다.
- 검증. 단계마다 주 세션(춘식)이 만들고, 짝 Codex가 코드 정독과 시험 재실행, 실제 기록에 대한 독립 대조를 맡는다. 짝은 단계마다 새로 만든다.
- 개인정보. 이 PC의 기록 본문, 사용량 숫자, 메일, 실명은 저장소와 병합 요청에 넣지 않는다. 실측 결과는 저장소 밖의 작업 기록에 둔다.
- 원장. 단계마다 Task Master 원장(`.taskmaster/tasks/tasks.json`)에 과제로 올리고, 끝나면 상태를 고쳐 커밋한다.
- 상태 폴더. 상태 폴더(`~/.chunsik-garage`)에 새 종류의 파일을 두는 단계는 `aq where`와 `aq clean`(그리고 `--all`)이 그 파일을 다루게 같은 단계에서 고친다(설계 7.4).
